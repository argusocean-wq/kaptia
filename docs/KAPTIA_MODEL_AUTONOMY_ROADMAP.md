# Kaptia 模型自主化路線圖

## 核心決策

Kaptia 是最終產品模型與 AI 系統的名稱；Qwen 目前只是可替換的底層基礎模型。介面可以顯示 Kaptia，但工程文件、模型 manifest、授權清單和診斷資訊必須如實記錄實際權重來源。不得把品牌改名當成模型自主化完成。

## 分層架構

1. **Kaptia Base/Weights**：目前使用的第三方基礎模型及其微調權重；明確記錄模型 ID、revision、量化格式、tokenizer、授權及檔案雜湊。
2. **Kaptia Training**：經授權、去識別化、品質審核的指令資料與程式碼資料；分離 train/validation/eval，避免洩漏；保留訓練參數與可重現日誌。
3. **Kaptia Reasoning**：可插拔的推理策略（單次生成、有限候選比較等），所有策略有預算上限、可回退，不能繞過憲法或工具權限。
4. **Kaptia Knowledge**：版本化本機知識包與 RAG，來源與雜湊隨檢索結果保存。知識更新不應只靠重新訓練模型。
5. **Kaptia Constitution/Policy**：安全、著作權、隱私、誠信與權限規則；提示層之外，逐步加入輸入/輸出檢查與工具層強制限制。
6. **Kaptia Runtime**：Windows Python 與 iPhone Safari/Transformers.js 是不同執行目標，需分別測試；不能假設同一權重格式可以跨平台直接使用。
7. **Kaptia Evaluation**：固定的繁體中文、推理、程式碼、知識依據、安全、著作權、提示注入與拒答測試集；記錄基準模型和每個候選版本的結果。

## 演進階段

### Phase 0 — 身分與可重現性
- 所有 UI 與產品文案以 Kaptia 為產品名稱。
- 技術 manifest 保留實際 base model、revision、tokenizer、量化與授權資訊。
- 設定明確模型介面，讓推理策略與 UI 不綁死某個供應商。

### Phase 1 — Kaptia 系統模型（當前可行）
- 維持可替換的底層模型，整合推理流程、知識檢索、記憶、工具權限、安全政策與交付驗證。
- 加強高風險操作的程式層限制；模型輸出不能自行授權工具。
- 建立固定 benchmark，記錄品質、延遲、記憶體、拒答正確性與回歸。

### Phase 2 — Kaptia 微調權重
- 先驗證資料、授權、重複與 train/eval 洩漏，再執行 LoRA/QLoRA。
- 以未參與訓練的固定測試集做盲評；只有量測結果支持時才接受新 adapter。
- adapter 合併成功不代表能力提升，也不等於獨立基礎模型。

### Phase 3 — Kaptia 發布模型
- 建立獨立模型版本、manifest、模型卡、資料摘要、已知限制、授權聲明及權重雜湊。
- 完成獨立權重匯出與相容性測試；瀏覽器 ONNX/量化是另外的建置與驗收流程。
- 不得在訓練、評估、轉換或真機測試未完成時標示為成功。

### Phase 4 — 評估是否訓練自己的基礎模型
- 只有在有足夠合法高品質語料、算力、訓練預算、資料治理與評估能力時才評估從頭預訓練。
- 從頭訓練不是目前的預設工作；小型資料集上的 QLoRA 不能取代基礎模型預訓練。
- 若仍基於第三方權重，Kaptia 可是有自主系統、微調權重與評估標準的模型產品，但必須透明說明其來源。

## 完成條件

只有當某個 Kaptia 版本具備版本化權重、可重現訓練/轉換紀錄、通過固定驗收集、經人工盲評、授權審核與目標裝置端到端測試，才可以宣稱該版本達到相應的發布狀態。CI 通過只證明 CI 所執行的檢查通過，不等於真實模型品質或裝置相容性已驗收。
